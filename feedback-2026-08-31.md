# Field feedback — 2026-08-31

Session: nvtauri, building a new mode with the `herdr-subagents` skill as
coordinator. Three children over the session (two `worker`, one `reviewer`,
all `--model opus`), plus `SendMessage` steering mid-build. Written by the
coordinating Claude session so the harness can improve; the user asked for it.

## What worked well

- **The callback contract is solid.** Every child read its brief, did the
  work, and its final message arrived as a `<cross-session-message>` that
  started a new turn here — including from children the registry had lost
  track of (see below). Nothing was ever polled.
- **`SendMessage` steering by name worked first time**, both to a registered
  child and to an unregistered one; the backend worker folded the frontend's
  IPC notes into its build without a round trip.
- **Role tool policies did their job.** The `reviewer` fixed nothing and
  reported nine ranked findings with file:line and a verdict, exactly the
  shape the skill tells you to ask for.
- `doctor` was quick and green.

## Snag 1 — `spawn` closes the tab of a child that is starting fine

**Observed.** Two `spawn --role worker --model opus` attempts in a row failed
with:

```
hs: could not start 'bc-rust'; tab w19:t2 closed.
    timed out waiting for agent startup Ownership retained for diagnosis at
    …\claims\names\bddb09…; transcript claim: …\claims\sessions\99c1e1….
    Stop/inspect before recovery.
```

`doctor` reported everything `ok` between the attempts. A third child that
happened to be spawned in the same shell call survived — because my shell's
own 2-minute timeout killed `hs.mjs` *before* its startup wait expired, so it
never got to close the tab. That child went on to complete its task.

**Cause.** `claude-plugin/scripts/hs-lib.mjs`, `startAgentInPane()`:

```js
["agent", "start", name, "--kind", "claude", "--pane", paneId, "--timeout", "60000", "--", ...agentArgs]
```

The 60 s is hardcoded. On this machine, with an nvtauri build and another
Claude session running, a Claude Code child with Opus and the full plugin set
takes longer than that to be *detected* as started. Herdr's `agent list` also
kept `"launch_pending": true` on the surviving child for its whole life while
reporting `"agent_status": "working"`, so whatever `agent start` waits for may
never flip on this setup.

**Workaround I used** (ugly, but it shipped the feature):

```bash
timeout 50 node ~/.claude/herdr-subagents/hs.mjs spawn --role worker --model opus --name bc-back …
```

Kill `hs.mjs` before its own timeout fires; the tab and the agent survive.
Costs: the child is absent from `hs.mjs list` / `result` / `stop` (the
registry entry is written after the wait), so tabs had to be closed with
`herdr tab close <tab_id>` after looking them up in `herdr tab list`.

**Suggestions.**

1. Read the timeout from an env var (`HS_AGENT_START_TIMEOUT_MS`) or a
   `--start-timeout` flag, default higher than 60 s for Opus.
2. Better: treat `agent_status: working` (or the reply address being echoed
   back) as the startup signal, and let `agent start`'s own wait be advisory.
3. Write the registry entry *before* the startup wait (mark it
   `startupUncertain`), so a killed or timed-out `hs.mjs` still leaves a
   usable `list`/`stop`/`result` entry rather than a live tab the registry
   denies exists.
4. Don't close the tab on a timeout when `herdr agent list` shows the agent
   as `working`; retain it and say so.

## Snag 2 — a failed spawn poisons its name

After the timeout, the name claim is "retained for diagnosis", and the next
`spawn --name bc-rust` hit the same wall. `stop` + `forget` cleared it, but
the message doesn't say that is the recovery, and I ended up using a fresh
name (`bc-back`) to be safe. A one-line hint — "run `hs.mjs stop <name>` then
`forget <name>`, or pick another name" — would save a round trip.

## Snag 3 — `list` and Herdr disagree about who is alive

With the surviving unregistered child running, `hs.mjs list` said `no
subagents owned by this session` while `spawn --name bc-front` was refused
with `explicit name 'bc-front' is already live`. Both are correct from their
own source (registry vs. `herdr agent list`), but together they are
confusing. An `adopt <name>` command — re-register a live Herdr agent that
was launched by this session's claim — would close the gap; so would `stop`
accepting a tab id.

## Snag 4 — the skill's "fan out in ONE Bash call" advice interacts badly with 1 + 2

With startup taking ~60–90 s per child, three spawns in one shell call run
serially for 3–5 minutes, longer than a default 2-minute tool timeout, and a
killed shell leaves the later spawns half-done (which is exactly how Snag 1's
survivor happened). Either spawn in parallel inside `hs.mjs`, or the skill
text should say to raise the shell timeout or spawn one per call.

## Minor

- `spawn --help` prints `spawn needs --role <name>`; a real usage line with
  `--model/--effort/--add-dir/--name/--cwd` would help when guessing flags.
- `doctor` could time a real `agent start` round trip; it was all `ok` while
  spawn could not succeed.
- The skill says `--add-dir` for reaching outside `--cwd`; it worked for a
  spec file in the session scratchpad. Worth stating that the brief and the
  add-dir are both delivered without a permission prompt when they are.

# Second session, same day — real-exec, the comb11e go-live review

Session: real-exec (Claude Fable 5) as coordinator of a fractal loop, win11,
Herdr workspace `w1C`, six children requested in the first wave (three `scout`
at `--effort medium`, three `worker --model opus --effort high`). Written by the
coordinating session at the user's request. It reproduces Snags 1-4 above
independently and adds three observations.

## Reproduction of Snags 1-4

- **Snag 1, four times out of five.** `spawn` returned `timed out waiting for
  agent startup ... tab closed` for `c11-s1-state`, `c11-s3-prop`, `c11-s1b-state`
  (a retry without `--add-dir`, so the extra directory was not the cause) and,
  in a killed batch, `c11-w1-contrib`. Two of the "failed" children were alive:
  `c11-s2-legs` ran its whole 15-minute task and reported by cross-session
  message, and `c11-w1-contrib` started as an orphan, ran a 70-minute task in
  parallel with the Agent-tool worker holding the same claims, and overwrote its
  script mid-run. Both copies reproduced the pinned row to four decimals, which
  is the only reason it cost nothing.
- **Snag 2.** The retry of `c11-s1-state` was refused (`already owned`); the
  claim files under `claims/names/` and `claims/sessions/` had to be left for
  `forget`, which itself refused until `stop`.
- **Snag 3.** `hs.mjs list` showed only the registered children (two, both
  stopped); `herdr agent list` showed the two live orphans, one with
  `launch_pending: true` for its whole life. `hs.mjs stop` refuses an
  unregistered tab; `herdr tab close <tab_id>` is what closed them.
- **Snag 4.** Six spawns in one Bash call hit the tool's 2-minute timeout on the
  first spawn's 60-second wait plus its cleanup; the batch was later killed
  mid-way, which is what produced the orphans. `run_in_background` on the
  spawning shell avoids the tool timeout but not the orphan.

## What worked

- `hs.mjs resume c11-s1-state` on a startup-timed-out child brought it back
  idle in a new tab in under a minute, and the two-step form (`SendMessage`
  with the whole task and `notify_when_idle: true`) delivered the task; its
  fact sheet came back as a cross-session message. So the transcript and
  session behind a "failed" spawn are intact; only the detection failed.
- The one scout that ran end to end returned exactly the shape the task asked
  for (paths, line numbers, "not found" over a guess). The visible tab is the
  reason the user wanted herdr; when it worked it was worth it.
- `doctor` was all green before, during and after the failures, as in the
  first session; it does not exercise a spawn.

## Three observations not in the first session

1. **The `scout` role has no shell.** `c11-s1-state` reported "this session
   has Read/Glob/Grep only, no shell/python execution", so a quant scouting
   task (read twelve pickles' first and last trade dates with the repo's own
   loader) could not be done; it fell back to a file census. A read-only Bash,
   or a `--tools` flag on `spawn`, would make the role usable for anything that
   needs one `python -c`. The fractal `fractal-scout` role has Bash and did the
   same job through the Agent tool.
2. **The Agent tool was the reliable runner on this box.** After the first
   batch, nine workers, two verifiers and one senior ran as Agent-tool
   subagents with no failures; the trade-off is that nothing is watchable. A
   coordinator under a clock will make that trade every time. Until Snag 1 is
   fixed, the skill should say so instead of presenting the tab as the
   default.
3. **A killed spawn batch needs a recovery command.** After the batch was
   killed, the only way to find what it had started was `herdr agent list`
   plus reading tab titles. `hs.mjs adopt <tab_id> --name <name>` (register an
   orphan so `list`, `result`, `stop` see it) would have closed the gap in one
   call; so would `spawn` writing its registry entry before the startup wait
   rather than after.

## Suggested fixes, in order of payoff

- Register before waiting; on detection timeout keep the tab and mark the
  entry `starting` instead of closing it (Snag 1 + 3 in one change).
- Raise or expose the 60 s in `startAgentInPane()`; `--startup-timeout` on
  `spawn`.
- `spawn --no-wait` returning after tab creation, so a batch of five takes
  seconds and the Bash tool never kills it.
- `doctor` runs one real spawn of a trivial `scout` and reports the detection
  latency it measured.
- `scout` gets read-only Bash, or `spawn --tools`.

# Resolution — 2026-08-31, commit `ad3b352`

Fix session in this repo, working from both reports above. `npm test` (186) plus
each change exercised against real Herdr 0.8.2-preview in workspace `w1F`.

## The half neither report had

Herdr assigns the agent **name** only when `agent start` succeeds. After a
detection timeout the child is live and `idle` in `herdr agent list`, but
nameless — `agent get <name>`, `agent read <name>` and every other
name-addressed command answer `agent_not_found`. That is why
`herdr agent read <handle>` returned nothing on a failed spawn in either
session, and why `hs.mjs list` could never resolve such a child. Its `pane_id`,
which `tab create` already returns, is the handle that still works;
`agent get <pane_id>` gives back the full record, pinned session id included.
`SendMessage` was never affected — Claude's name registry comes from `--name` —
which is why steering an "unregistered" child worked first time.

## Snag by snag

- **Snag 1.** `agent_pane_busy` is now the only outcome treated as proof that
  nothing started, and the only one that closes a tab. Everything else asks
  `agent get` by name, then by pane, before believing the timeout. The budget is
  `--startup-timeout` / `HS_AGENT_START_TIMEOUT_MS`, default 90 s, validated
  against Herdr's own limits (it rejects ≤3000 and >300000 ms).
- **Snag 1 + 3.** The registry entry is written *before* the wait as
  `startupUncertain`. A batch killed mid-detection no longer leaves a child that
  `list`, `result` and `stop` each deny exists. `list` also resolves status
  through the pane, so `starting` clears on its own, and names live agents in the
  workspace this session does not own.
- **Snag 2.** The failure prints its recovery — `stop`, then `resume` to retry or
  `forget` to free the name — and points at the pane, not the name.
- **Snag 3.** `adopt <name>` re-registers a live child, keyed on the name claim
  rather than the tab, so it cannot seize another session's child. `stop` still
  refuses a bare tab id; `adopt` covers that case without weakening the guard.
- **Snag 4.** `spawn --no-wait` returns once the child is launched. Three real
  spawns measured 16.4 s end to end, against the 3–5 minutes that was killing the
  batch.
- **Minor.** `spawn --help` documents every flag. `doctor --spawn` launches a
  throwaway haiku scout and reports the detection latency it measured — 5.3 s
  here against the 90 s budget. Every static check stayed green through both
  field failures, which is the point.

## The one suggestion that does not work

`scout` cannot be given a read-only shell. Verified against claude 2.1.251: an
agent declared with `tools: [..., "Bash(node --version:*)"]` reports plain `Bash`
in its own tool list and runs `echo` happily under `--permission-mode auto`. The
specifier is decoration, so a scoped entry would be a full shell wearing a
read-only label. `scout` keeps no shell; recon that has to run a command is a
`worker` whose task says to change nothing. `spawn --tools` would be the same
trap and was not added.

## Left for a future session

- `--add-dir` and the brief arriving without a permission prompt is still
  undocumented in the skill.
- Nothing here was tested on a *loaded* box. The failures both reports saw were
  load-dependent; on an idle machine detection is 5 s against a 90 s budget, so
  the raised default is untested at the margin it was raised for. A field session
  under real load is the next evidence worth having.
